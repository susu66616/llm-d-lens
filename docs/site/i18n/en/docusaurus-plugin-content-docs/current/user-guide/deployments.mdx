Open **Deployments** to check whether a model is ready, inspect a failure, or manage an existing deployment.

P/D deployments using Router 0.11 automatically adapt legacy plugin settings when
created or retried. The original configuration is retained, and deployment
diagnostics record the effective Router values. A legacy `disagg-headers-handler`
entry is replaced by the profile handler's built-in header handling; the saved
prefill/decode decision is preserved. A conflicting old and new decider setting
must be corrected before deployment.


## Configure and review Manual or Agentic plans

Choose **Manual** or **Agentic** in the two prominent mode cards, then reuse
the compact environment card. Lens preselects a ready cluster when available, generates the
deployment name and checks the selected model cache. **Change setup** opens cluster, name and model-cache controls together. An unavailable model cache still requires preparation.
Neither mode asks for hardware specifications or a Guide before planning.

**Build Manual plan** combines applicable, supported compatible optimizations and
opens the reviewed configuration. Agentic offers Balanced, Low latency and High
throughput on the same entry screen. **Build Agentic plan** opens the generated plan
directly, with no intermediate questionnaire. Keep Balanced to continue without parameters. A restored plan preserves other supported objectives.
**Describe a goal** optionally enables natural-language goals with an explicit AI
provider; otherwise Agentic uses rule-based recommendations. The interface identifies
which path is selected. Neither path establishes a measured optimum.

Resource limits, workload, request sizes and latency targets are collapsed optional
sections. Blank inputs remain unspecified; saved constraints remain visible when
reopened. The **1–3 Walkthrough** highlights mode, setup and continuation controls.
The plan's **Walkthrough** highlights its summary, serving flow and unified review
action without generating, changing or approving a plan for you.
Skip or Escape closes the overlay; highlighted controls remain usable.

The generated plan prominently retains **Manual plan** or **Agentic plan** alongside
the model and cluster. Use **Change setup** to return to setup; existing
backend plans remain saved under their original mode and target.
The **Serving flow** shows a horizontal Request → Endpoint selection → Prefill → Decode → Response path.
Combined serving places both compute phases inside one Model server boundary; P/D uses separate boundaries.
Cache indexing, KV cache, compute configuration and service management connect to the stages they affect.
These are logical processing and configuration relationships, not live traffic or measured placement.

Every functional group is visible, with configured counts and a short summary. Select a group to expand
its optimizations inside the diagram, including off and unavailable entries. Each group has its own pages
of up to four settings; expanding another group collapses the previous one. Select an optimization to open
its source, router or runtime parameters in a configuration drawer. **Stage parameters** inside an expanded group opens broader settings such as replicas, when declared by the source. Supported toggles and detailed editors
use the existing compatibility checks. Unavailable settings explain their status and remain read-only.
There is no separate Stage configuration table or global All settings visibility switch.
Apply edited parameters and check resources before reviewing deployment. Closing the drawer keeps unapplied
changes visible in the plan; discard them explicitly if needed. Narrow screens can scroll the diagram horizontally.
The optional **3D technical view** retains the infrastructure topology.

Use **Refine with Agentic** when the current plan does not fit your goal. Choose an objective and optionally
adjust the existing workload and limits. The same model, cluster and runtime inputs are carried into a separate
recommendation; exact source edits remain in the previous plan. **Return to previous plan** restores that saved
plan without regenerating it. Apply or discard pending edits first. Recommendations still require resource checks
and explicit deployment confirmation; no performance result is implied. This return history lasts while the setup
page remains open. The mock supports objective selection only and uses simulated rules. Prefix caching and Chunked prefill expose an **Enabled / Disabled** control with an argument preview. **Apply changes** updates the mock plan and YAML; **Cancel** discards that edit. Other unsupported mock settings explain why they are unavailable.

**Technical details: source Guides and all parameters** contains the complete
Guide index from the cluster's pinned llm-d revision.
Unavailable, external-operation and unadapted Guides retain their explanations:
being listed does not promise that a Guide or arbitrary combination can deploy.
Selected Guides expose their compatibility choices and source variables.
The flow includes independent prefix affinity and precise cache indexing.
The configuration drawer exposes only the selected node's source/router or runtime fields,
including per-replica native CPU cache capacity. Source variants remain editable.
**All deployment parameters** in Technical details includes the complete rendered
parameter list and **Final YAML** editing.

Automatic additions retain each candidate's sized serving topology. A different
topology is compared as a separate candidate, not substituted while retaining the
old role parameters. Inventory controller installation requires explicit selection.
Unsupported transport/cache combinations remain excluded without blocking compatible
alternatives; required user selections are never silently dropped.
The Router's narrowly scoped authentication RBAC is managed with the deployment
namespace. Cleanup also waits for these resources to be garbage-collected; an
ownership conflict is an error, never permission to replace an existing grant.

Manual selects compatible source optimizations without using workload benefit as
a gate, while preserving explicit exclusions and edits. External prerequisites,
unresolved choices and resource checks still constrain generation. Agentic uses
the workload recommendation and the same editor; both modes include compatible
source additions beyond workload presets without automatically installing external
prerequisites. **Apply changes and check resources**
creates a new reviewed source snapshot; unapplied edits block deployment. Changing
selections preserves unrelated final parameter edits by reconciling them with the
newly rendered resources. Conflicting edits block application with an explicit
error instead of silently disappearing; undo the conflicting selection or use
**Discard final parameter edits** in Technical details. Legacy snapshots without
an edit baseline require explicit resolution when their base configuration changes.
Disabling native CPU cache retains its capacity for re-enabling.
A changed source revision requires an
explicit decision to discard source edits and adopt the current revision.

A compact strip above the serving flow summarizes topology, resources, optimization
count and validation. **Review & deploy** opens the YAML and **Deployment summary**
together in one dialog, including capacity, cache, warnings and **Confirm deployment**. Select
the model-serving **Inference Service**, not EPP or metrics. Approval binds the
selected endpoint and exact configuration checksum and rechecks capacity; editing
does not provide a separate deploy path. Legacy saved plans expose **Load Guides
and build source configuration** and retain their old preview in a disclosure.
If the source catalog is unavailable, the error remains visible instead of
silently presenting legacy templates as a fully supported source composition.
The collapsed **More planning tools / optional** entry retains Agentic **Alternatives**
and **Benchmark tests**. Alternatives compares reviewed source configurations and evidence.

For Agentic plans, **Benchmark tests** is a separate optional view. Prepare a
test-enabled plan there before selecting the workload and confirming tests.
Its accelerator ceiling starts from the planning constraint or discovered capacity;
unknown capacity requires an explicit value. Saved tests restore their recorded
workload and budget. The form checks required repetitions, resource ceilings and
numeric limits before submission. Interrupted or failed cleanup must be resolved
before starting more tests; submitted deployments cannot start another trial.
Trial evidence displays measured TTFT, TPOT, end-to-end latency, throughput and
error fraction, with missing values left unknown.
For source-backed plans, **Check all source candidates** renders each candidate
before testing, and each selected candidate requires its reviewed inference
Service. Cache variants must be edited and rendered in the Guide configuration;
tests do not silently add an unreviewed native-cache variant. Choosing a measured
winner restores its exact reviewed source configuration.

**Workload and limits** shows the discovered capacity and current context setting
without inventing traffic values. Accelerator limits can change which combinations
fit; request sizes and concurrency refine capacity estimates; QPS and latency set
performance targets. Blank fields impose no additional constraint.
Use **Rebuild plan** to apply overrides. The collapsed **Planning log** retains
diagnostic events; Manual has no redundant single **Plan** navigation button.
The current plan remains available until a replacement is
created; **Keep existing plan** returns to it. A new configuration revision requires
new review. **Review & deploy** opens one review for the exact displayed configuration.
Use **Confirm deployment** to submit; a changed checksum requires a fresh review.
After confirmation, **Deployment execution** shows the actual Deploy
run and component states, attempts and failures. Open **View Pods & Logs** when an
execution record is available, or **Open deployment** to open the filtered
Deployments list for monitoring and further evaluation.
The summary reports **Deployment ready** only when Deploy succeeds and every
component reports ready; planning status alone is not readiness. Workload
performance still requires measurement.


## Hardware profiles and guide variants

Deployment rendering resolves hardware through the profile registry. The selected
profile supplies the runtime image, scheduling labels, accelerator resource request
and PCI-selection capability. Custom runtime images remain user-controlled; unknown
hardware does not silently select another vendor's defaults.

Guide variants come from actual Kustomization entry points in the selected llm-d
repository revision, including nested overlays. Changing hardware or source can
change the available variants. A listed overlay can still require cluster resources
such as NIC device classes, storage or runtime support; planning validates these
requirements before deployment.

Automatic generic entry selection prefers the root (`.`), then `base`. If neither
exists, deployment reports the Guide, hardware profile and available variants
instead of silently choosing a platform-specific overlay. Select a compatible
Guide source or explicitly choose a listed variant where supported.

Agentic tiered prefix cache requests native CPU caching without pinning the source
layout. Lens resolves `native/cpu` or `native/cpu/base` from the selected source and
accepts the legacy path. Missing native CPU entries produce an error; Lens never
substitutes another cache implementation, storage tier or platform overlay.

The deployment list cancels superseded filter requests so older results cannot replace the current selection. Cluster names are shown when available, with IDs as a fallback. Deletion still requires the displayed confirmation phrase and preserves the namespace choice; while deletion is pending, submission and dialog dismissal are disabled.

When specifying an operator preference for deployment planning, use English, such as
`prefer prefix cache`, `more GPU for performance`, or `use fewer GPU resources`.
The deterministic planner matches English preference keywords; Chinese keyword aliases
are no longer supported.

## Open the deployment creation flow

Manual proceeds directly to **Deployment plan**; Agentic first offers an objective,
with all numeric parameters optional.
No request lengths, prefix reuse or workload shape are invented. These are benefit
hints, not compatibility gates. Agentic
can interpret explicitly stated qualitative workload traits from a goal when an
AI provider is selected; the interpretation is displayed and editable. Without AI,
use structured inputs. Numeric resource and performance limits are never inferred.

Manual chooses the greatest source-verified capability coverage among supported
combinations, not the first Guide that renders. It does not maximize resource use
or claim a measured performance optimum. Unsupported combinations remain explicit.
**Ready for your confirmation** is a compact conclusion; failed checks block deployment and
provide **Retry checks**. Deployment confirmation rechecks current capacity.

Prefix-affinity routing, P/D separation and CPU KV offload can be combined independently.
Routing composition retains the P/D profiles and uses affinity plugins from the same
pinned source revision; incompatible plugins or images are reported explicitly.
Basic attention KV caching is distinct from cross-request prefix caching and CPU
offload. Missing explicit vLLM flags can be configured with a mandatory startup
capability probe in the selected image; this is not a claim of verified runtime support.

Deployment creation requires models registered in [Model Cache](/user-guide/model-cache).
Select a registered cache volume containing the ready model and its revision on the
same cluster. The Advanced configuration editor has only the **Model Cache** source.
For local-disk storage, synchronize new nodes before deployment. Ordinary provider
rendering configures offline serving with a read-only cache mount. Download
or repair the cache in Model Cache first, then create or retry the deployment.

Cache checks follow the active serving roles: P/D checks Prefill and Decode
independently; other providers use Decode. Each role defaults to revision `main`.
An explicit tokenizer must also be ready in the same cache volume; its revision
defaults to the role's model revision unless `tokenizer-revision` is supplied.
Conflicting dependency arguments are rejected. The rendered model and tokenizer
arguments must match the checked dependencies before deployment proceeds.

Ordinary optimized-baseline rendering does not apply custom `revision`, `tokenizer`,
or `tokenizer-revision` arguments, so those inputs are rejected. Configuration-source
overrides and custom `model`, `model-path`, `code-revision`, `hf-config-path`,
`config`, and `download-dir` arguments are not supported by cache preflight.

### Model Cache enforcement limitations

Exact published YAML configurations (`officialGuide`) bypass ordinary provider
rendering. Their final manifests do not yet enforce the same offline flags,
read-only cache mounts, or backing-volume binding. Cache-only deployment is
therefore not guaranteed for this path. Offline environment variables are also
not a network isolation boundary.

1. In the left navigation, open **Deployments**.
2. In the page header, click **Create**.
3. Follow [Create a deployment](/user-guide/model-market). The new deployment appears in this list after submission.

The shared creation workflow uses the soft same-node placement preference.
Existing deployment APIs and the separate Configuration editor retain their
placement controls. TP devices are requested by each model-server Pod; planned
placement is not shown as actual cluster placement before deployment.

## Find a deployment in the list

1. Review the summary cards at the top of the page: **Total**, **Ready**, **In progress**, **Failed**, and **Cleaned**.
2. In the list toolbar, type in **Search deployments** to match a deployment by name, description, model, namespace, guide, or ID.
3. Open **Status** to filter by deployment state.
4. Open the cluster selector and choose **All clusters** or one cluster.
5. If needed, change **Rows per page** and use the pager to move through the list.
6. If no rows match, click **Clear filters**.

The **Cluster** and **Namespace** columns each include a copy button.

## View deployment details

1. In the deployment row, open the actions menu and select **View details**.
2. In the drawer, review the sections **Basic Information**, **Model & Serving Engine**, **Cluster & Environment**, **Network & Endpoints**, and **Audit & Timeline**.
3. Use the copy buttons beside values such as **Namespace**, **Cluster Session ID**, **Container Image**, **Internal Endpoint**, **Forwarded Endpoint**, or **Execution ID** when you need to reuse them elsewhere.
4. If the deployment failed, read the failure banner before making changes.

Wait for **Ready** before calling the deployment. For **In progress**, check the pod logs for startup progress. For **Failed**, read the failure banner and the affected pod's logs.

The status dot also reflects live model-server Pods. A yellow dot means fewer ready model-server Pods than requested, so serving capacity is reduced. A red dot means no ready model-server Pods remain, so the service is unavailable. These conditions are also reported under **Needs attention**.

**Failed** is not final. A rollout that ran past its progress deadline is recorded
as failed, but the workload often recovers on its own -- a pod that kept crashing
until its model cache was complete, for example. Lens keeps re-checking failed
deployments against the cluster and flips them back to **Ready** once their pods
serve again, so leave the deployment in place rather than recreating it
immediately. If the namespace is gone, the deployment is corrected to **Cleaned**
instead.

Pending Pods waiting for accelerator resources, including DRA scheduler reports
such as `cannot allocate all claims`, keep the deployment **In progress** even
after the rollout progress deadline. Refreshing a deployment previously marked
**Failed** returns it to **In progress** when current diagnostics confirm this
resource wait. The scheduler reason remains available in diagnostics. This does
not release devices held by other deployments; stop or remove an unused deployment
to free them. Container crashes and image-pull failures still count as failures;
Pending alone is not enough to classify a deployment as waiting for resources.

After scheduling, a Running Pod can still be loading the model and not yet Ready.
If rollout reports an exceeded progress deadline, Lens preserves **In progress**
without automatic cleanup while current containers remain within their
`startupProbe` budget (or `readinessProbe` budget when no startup probe exists),
measured from each container's actual start time. Time spent Pending does not
consume this budget. Current crashes, image-pull failures, container restarts and
expired probe budgets are not covered by this grace period. Running alone is not
proof of readiness; the provider's readiness checks must still pass.

## View pods and stream logs

For newly rendered deployments, all providers forward explicit maximum model
length, maximum sequence count, GPU memory utilization, block size and maximum
batched tokens to vLLM. P/D applies Prefill and Decode settings independently.
Role settings override Guide defaults; model-level maximum length is a fallback
when the role does not specify one. Targeted custom arguments take precedence.
Omitted settings retain upstream defaults. These changes do not rewrite existing
Pods or exact published manifests: create a new deployment to apply changed settings.
Check the model-server command and logs when diagnosing KV-cache capacity errors.

Lens checks `/dev/shm` in rendered model-server Pods across all deployment
providers. Ordinary rendering adds a per-Pod, memory-backed `emptyDir` with a
**4 GiB** limit when the mount is missing and host IPC is not enabled.
`baseline-vllm` also defaults to 4 GiB. This avoids the container runtime's
default 64 MiB shared-memory limit without enabling host IPC or changing
the upstream Guide checkout.

Existing mounts and their limits are preserved, including mounts with no explicit
limit and alternative volume sources. Missing limits, alternative sources,
read-only/subpath mounts and existing host IPC produce warnings in service logs
and deployment diagnostics (`snapshot.shared_memory`). An omitted `sizeLimit`
on a memory-backed volume does not mean a 64 MiB limit or unlimited usable memory.
Duplicate `/dev/shm` mounts and invalid volume bindings are rejected.

Exact published manifests (`officialGuide`) are checked but never receive an
automatic shared-memory mount; missing mounts produce warnings instead.
The report is also retained in the deployment artifact's
`rendered_payload.value.deployment_contract.sharedMemory`.
Volumes consume memory as used, not their full limit up front; account for
shared memory when sizing Pod memory. Existing deployments retain their original
manifests; recreate them to receive the new default or missing-mount completion.

1. To see pod status inline, click the row toggle with tooltip **Show pods**.
2. In the expanded row, review the pod table columns **Pod**, **Status**, **Restarts**, **Node**, and **Pod IP**.
3. For the full log viewer, open the actions menu and select **View pods & logs**.
4. Use the node filter or search fields to find the pod.
5. Click a pod card to open **Pod Logs:** for that pod.
6. If a pod has multiple containers, choose the needed **Container: ...** entry.
7. Select **100 lines**, **200 lines**, **500 lines**, or **1000 lines** to change the log tail length.
8. Turn **Previous** on if you need the previous container log.
9. Leave **Auto-refresh (5s)** enabled to keep the pod list and logs live.
10. Use **Filter log lines...** to narrow the log output, or click **Copy** to copy the current log text.

## Graceful shutdown defaults

Lens creates model-server Pods with a **120-second** termination grace period and a **5-second preStop delay**. vLLM containers also receive `--shutdown-timeout=90` when their invocation is a single recognizable `vllm serve` or `python -m vllm.entrypoints...` command (including `sh -c` scripts); compound shell scripts, unrecognized entrypoints and non-literal existing values are left unchanged with a deployment warning. During scale-down, rolling updates or node drains, Kubernetes removes the Pod from routing first; vLLM can then finish in-flight requests for up to 90 seconds before termination. Deployments created before these defaults were introduced must be restarted or recreated to receive them. SGLang does not support the vLLM flag, so only endpoint removal and the grace period apply. For P/D deployments, scale down decode before prefill. When a model container has a `--kv-transfer-config`, Lens sets `kv_load_failure_policy=recompute` in that JSON so Decode can recompute a failed Prefill KV transfer.

## Scale a deployment

1. In the deployment row, open the actions menu and select **Scale deployment**.
2. For a P/D deployment, set **Prefill replicas** and **Decode replicas**. For an aggregated deployment, set **Replicas**.
3. Click **Scale deployment**.

Manual scaling changes live Kubernetes model-server replicas only. Restarting the deployment restores its configured replica count. DisaggregatedSet deployments are created with `slices: 1`; manual scaling changes role replicas and never changes `spec.slices`. For a P/D deployment, scale down Decode before Prefill; Prefill scale-down can interrupt in-flight KV transfers, but Lens configures `kv_load_failure_policy=recompute` whenever a `--kv-transfer-config` is present.

## Model inference access

Deployment sharing is no longer supported. Admin and maintainers manage
deployments within their cluster scope. Consumers do not get deployment pages
or direct deployment access; publish a model service and use its
[Manage access drawer](/user-guide/model-services#manage-model-access) to grant
inference to users or groups. Old deployment shares are not automatically
converted into model grants.

## Delete a deployment

1. In the deployment row, open the actions menu and select **Delete deployment**.
2. In **Delete deployment**, review **Execution ID**, **Cluster**, and **Namespace**.
3. Leave **Also delete the Kubernetes namespace** checked if you want Lens to remove the namespace and everything inside it, or clear it to remove only the deployment record.
4. In **Type `<phrase>` to confirm**, enter the exact confirmation phrase shown in the dialog.
5. Click **Delete deployment**.
6. If you do not want to continue, click **Cancel**.

## Related references

In the deployment creation flow, expand **Why this option** under a validated alternative to see its AISimulate TTFT, TPOT, and throughput estimate when an exact-topology estimate is available. The estimate can appear even when the AISimulate candidate search finds no configuration satisfying the original SLO; in that case, the alternative still shows **SLO not met**. Alternatives without a matching estimate show that no exact AISimulate prediction is available.

The **AI score** shown beside an agentic candidate is a relative ranking score out of 100; the highest-scoring candidate is normalized to 100. It is not a benchmark result, confidence level, or probability of meeting the SLO. A deterministic fallback shows **Deterministic score** instead.

**Recalculate selection** works without an AI provider. It refreshes the recommendation
using deterministic planning and the new preference; if AI scoring fails, the
alternatives also retain deterministic scores.

Agentic alternatives are checked using the selected vLLM GPU memory utilization
and max model length. The same values are applied when the deployment starts;
actual free KV cache is measured by vLLM at startup and may still be lower than
the planning estimate.

If you use the agentic planner from the deployment creation flow, see the [Architecture overview](/architecture) for how workload-guided planning works.


## Verify profile-driven Guide configuration

Choose a cluster with downloaded Software Versions and refresh the page. The
hardware profile selects the Guide source root; the selected llm-d checkout
supplies its model servers and Kustomization variants, including nested paths.
Root overlays display as `Default (vllm)` or `Default (vllm-rdma)` instead of `.`.
Selecting a sibling runtime variant remains stable while editing other fields.

For official sources, cache and NIC controls appear after source preparation:
CPU capacity requires a supported cache connector in the rendered containers;
NIC count requires a claim matching the profile's NIC device class. Inspect the
generated YAML and source provenance before deployment. Access-mode settings
come from `deployment.modes`; DRA uses a device claim and plugin mode uses the
declared extended resource. User-selected runtime images remain overrides.

In Evaluation results, open Resources during benchmark. Device allocation
failures display a reason even when engine metrics are available. Plugin device
metrics require kubelet-reported, profile-recognized device identities; an
exporter alone cannot establish which devices belong to the workload. Profile
file edits require restarting the development services and refreshing the page;
this is not a live JSON editor. Existing saved results are not recollected.

## Review a generated deployment

Manual uses the source-backed editor described above. Prefix caching and chunked
prefill can be explicitly excluded without inventing workload characteristics.
Completion only changes source-supported settings; unavailable options retain
their reasons in the Guide and optimization inventory. Explicit runtime controls
remain authoritative. Guide composition supports optimized baseline, precise routing, and NIXL P/D plus native CPU KV cache from the same pinned official source. Runtime images must match. P/D wraps the original NixlConnector first and OffloadingConnector second in MultiConnector on both Prefill and Decode, preserving transport settings and reserving local host memory per model pod. A same-image init container checks connector imports and configuration schemas before startup; it rejects the known vLLM 0.19.0 offloading defect (upstream issues #39500/#39617). This check does not establish GPU correctness or performance. Unsupported transports produce an adapter-specific error; arbitrary connector stacking is not supported. Composition alone does not prove optimal performance.

The P/D CPU-cache adapter currently requires `NixlConnector` with `kv_both` on both roles.
Sources using `kv_producer` and `kv_consumer` remain eligible for P/D without CPU KV offload;
only the added cache combination is rejected. Lens does not rewrite these transport roles or
silently remove an explicitly requested cache requirement.

Use node parameter actions or **All deployment parameters**, then **Apply changes
and check resources**. Manual and Agentic both preserve the reviewed source bundle;
the editor does not silently send parameter changes to an LLM or substitute another
candidate. Explicitly rebuilding workload requirements requests a new recommendation.
Selecting an alternative is not deployment; **Review & deploy** still requires confirmation.

## Measure and compare Agentic candidates

Open **Verify with real benchmarks**, select candidates, set the GPU ceiling,
maximum minutes, benchmark-run budget and repetitions, then choose throughput,
P95 end-to-end latency or throughput per accelerator as the objective. Source-backed
candidates require reviewed inference Services and rendered cache variants. Only
legacy plans retain the optional CPU-cache budget that adds trial variants; include
those repetitions in their budget. Synthetic load starts from the plan's mean input/output lengths and concurrency;
missing values default to 512 input tokens, 128 output tokens and concurrency 4,
with 100 requests. A restored test uses its recorded workload. Expand
**Test workload** to change these values or supply representative inference-perf
YAML, such as a shared-prefix workload for cache experiments.

**Start deployment and benchmark tests** provisions actual cluster resources.
Each candidate is deployed, tested with the same workload and cleaned up before
the next candidate. Complete repetitions must satisfy every configured latency
SLO and the error limit. Missing metrics and failed trials never count as proof
of superiority. Results include benchmark IDs and a ranking of completed trials;
review the best measured candidate before confirming its final deployment.

Use **Stop and clean up** to cancel. Cleanup may outlast the measurement budget;
a cleanup failure blocks further deployment until resolved. Progress is audited
with the candidate configuration and workload. After a service interruption,
the recorded test task is marked interrupted and offers explicit cleanup; it
never automatically resumes deployment. Browser refresh restores the current
plan in the same session. This is bounded candidate search, not an unbounded
self-modifying optimization loop or a claim of global optimality.

The Overview and 3D tabs show each role’s transport and local CPU cache separately. Agentic CPU-cache trials include eligible P/D candidates and compare them with their original configuration using the same workload. The default NIXL-first order prioritizes transport when multiple connectors report a hit; it does not guarantee fewer network transfers. Confirm workload correctness and performance with real measurements.
